#+TITLE: Dockers

This repository contains Docker images that I regularly use. [[./Makefile][Makefile]] builds the
images and [[./aliases.sh][aliases.sh]] defines utility functions around them.

#+begin_src shell
source aliases.sh
make list
make web
#+end_src

Dependencies are wired up, so =make ad= builds /base-archlinux/ first. =mdm=
calls any Makefile target from any directory, with fzf completion and a
Dockerfile preview when /fzf/ is installed:

#+begin_src shell
mdm web                          # same as make web, from anywhere
make DOCKER_CMD=podman           # build with podman instead of docker
make web BUILD_ARGS=--no-cache   # extra flags passed to docker build
#+end_src

*Careful:* =make clean= is not scoped to this repository. It runs =docker system
prune -a -f= and then =docker volume prune -a -f=, so it removes every unused
image on the machine and every unused volume.

Sourcing /aliases.sh/ defines a function for almost every tool in these images,
and those functions shadow host binaries of the same name for the rest of the
shell session: =sqlmap=, =smbclient=, =ffuf=, =gau=, =gf=, =semgrep=,
=trufflehog=, =nxc= and =vsftpd= among them. Use =command <tool>= to reach the
host's own copy.

* bloodhound

Lets you run several [[https://github.com/SpecterOps/BloodHound][BloodHound]] instances easily. This one is a
=docker compose= project rather than one of the =make= images.

Copy the example environment file first and set an admin password: there is no
default for =bhe_default_admin_password=, and the first launch needs one.

#+begin_src shell
cp bloodhound/.env.example bloodhound/.env
$EDITOR bloodhound/.env      # at minimum: bhe_default_admin_password=
#+end_src

Remaining defaults live in [[./bloodhound/docker-compose.yml][docker-compose.yml]] and [[./bloodhound/.env.example][.env.example]]. The /.env/
you copy it to is gitignored, so real secrets stay out of commits.

#+begin_src shell
cd ~/projectA && bloodhound-run                          # ports 8111 / 7474 / 7687
cd ~/projectB && bloodhound-run projectb 8712 7475 7688  # name, then custom ports
#+end_src

Each instance keeps its data under the current directory, in
/.docker-bh-postgres/ and /.docker-bh-neo4j/, and is its own =docker compose=
project — so several can run side by side.

Commands: =pwn-run=, =pwn-runit=, =pwn-shell=. Inside the image, =gdb-pwndbg=
and =gdb-gef= start /gdb/ with the corresponding plugin; the bundled [[./pwn/files/gdbinit][gdbinit]]
also defines =openredir <file>= to redirect the inferior's stdin/stdout/stderr
to a file.

The image also ships a =pwn-init= command and two templates ([[./pwn/scripts/solve.py][solve.py]] and
[[./pwn/scripts/utils.py][utils.py]]) to bootstrap a challenge. =pwn-init= copies both into the current
directory (the mounted //work/), which is the first step for any challenge:

#+begin_src shell
pwn-shell                 # interactive shell, $(pwd) mounted at /work
pwn-init                  # drop solve.py + utils.py in the working directory
                          # pwn-init <dir>  targets another directory
                          # pwn-init -f     overwrites existing files
                          # pwn-init -s     also copy the solver skeletons
#+end_src

Edit /solve.py/ and set =BINARY=, =HOST=/=PORT= and the =SSH_*= block as
appropriate. Two more knobs sit further down the file: =context.gdb_binary=
chooses =gdb-pwndbg= or =gdb-gef=, and the =gdbscript= string holds the commands
gdb runs on attach. =GDB=, =REMOTE= and =SSH= below are command-line modes, not
variables to set:

#+begin_src shell
python3 solve.py          # run the binary locally
python3 solve.py GDB      # run locally under pwndbg
python3 solve.py REMOTE   # connect to HOST:PORT over TCP
python3 solve.py SSH      # run the challenge on the remote box over ssh
python3 solve.py SSH GDB  # debug it on the remote box via gdbserver
#+end_src

The =GDB= modes open gdb in a /tmux/ split, so start /tmux/ inside =pwn-shell=
first. Without it /solve.py/ writes the gdb commands to /.gdbscript/ and prints
the =gdb -p <pid> -x .gdbscript= line to attach by hand.

With =-s=, =pwn-init= also copies three solver skeletons: [[./pwn/scripts/angr_solve.py][angr_solve.py]],
[[./pwn/scripts/z3_solve.py][z3_solve.py]] and [[./pwn/scripts/sage_solve.py][sage_solve.py]].

#+begin_src shell
pwn-init -s               # copy angr_solve.py + z3_solve.py + sage_solve.py
python3 angr_solve.py
python3 z3_solve.py
python3 sage_solve.py
#+end_src

Make sure to check out what [[https://github.com/nobodyisnobody/tools][nobodyisnobody]] implemented and thank him for the
great work!

as well as /recon.sh/ which runs all previous 3.

This builds the image and loads the commands (=recon=, =gimmesubs=, =http-probe=,
=nuclei-auto=, =subs2web= are shell functions from [[./aliases.sh][aliases.sh]]):

#+begin_src shell
source aliases.sh
make recon

cd ~/engagements/acme

recon acme.com ~/lists/big.txt                 # subdomain enumeration for acme.com
                                               # then identify http servers and
                                               # scan them with nuclei
recon --http acme.com ~/lists/big.txt 80,443   # stop after http-probe on port 80 443
recon --subdomains acme.com ~/lists/big.txt    # only subdomains

# the stages are standalone commands too
gimmesubs -p acme.com
http-probe acme.com_*/subdomains.txt
nuclei-auto http-probe_*/live.txt

# subs2web is gimmesubs piped straight into http-probe; anything after --
# goes to http-probe
subs2web -p acme.com
subs2web -a acme.com ~/lists/dns.txt
subs2web -p acme.com -- 80,443,8443
#+end_src

To run the image directly, without the wrapper functions (/massdns/ will need a
lot of ports):

#+begin_src shell
recon-run --help   # the image's own entrypoint, no argument rewriting
recon-shell        # interactive shell inside the image
#+end_src

** Configuration

API keys widen /gimmesubs/' passive phase. Every value is optional and a source
is only queried when its key is set:

#+begin_src shell
cp recon/.env.example recon/.env
$EDITOR recon/.env      # OTX_KEY, LEAKIX_KEY, DNSDUMPSTER_KEY, FULLHUNT_KEY
#+end_src

/subfinder/ keeps its own provider list in a separate file:

#+begin_src shell
cp recon/config/subfinder-provider-config.yaml.example \
   recon/config/subfinder-provider-config.yaml
#+end_src

Both files are gitignored. The wrappers bind-mount /recon/config/ read-only into
the container, so edits there take effect without rebuilding the image.

Wordlists are not baked in. Point =RECON_WORDLISTS= at a directory (it defaults
to /recon/wordlists/) and the wrappers mount it read-only at //wordlists/, which
also lets you pass a bare name instead of a path:

#+begin_src shell
export RECON_WORDLISTS=~/lists
gimmesubs -a acme.com big      # resolves to /wordlists/big.txt
gimmesubs -a acme.com dns      # a directory of lists works too
#+end_src

Rates and timeouts are environment variables, forwarded to the container when
set: =PASSIVE_TIMEOUT= (seconds per passive source), =HTTPX_THREADS=,
=HTTPX_TIMEOUT=, =HTTPX_RUN_TIMEOUT=, =NUCLEI_RATE_LIMIT=, =NUCLEI_CONCURRENCY=,
=NUCLEI_RUN_TIMEOUT= and =NUCLEI_EXCLUDE_TAGS=.

* semgrep

Docker installation of [[https://github.com/semgrep/semgrep][semgrep's]] cli with support for the pro version.

The pro engine needs an authenticated account, so the build runs =semgrep login=
and waits for you to open the URL it prints. Two things follow from that: the
build is interactive, and the token it obtains is written into an image layer,
where removing it afterwards does not get it back out. Passing
=SEMGREP_APP_TOKEN= in at runtime keeps it out of the image entirely.

To skip the pro engine, comment out *both* lines in the [[./semgrep/Dockerfile][Dockerfile]]:
=semgrep login= and =semgrep install-semgrep-pro=. Commenting only the first
leaves the install with no credentials and the build fails.

Commands: =semgrep= (the cli), =semgrep-pro-scan= (=semgrep scan --pro= with the
flags I use) and =semgrep-shell=.

Commands: =web-run=, =web-runit=, =web-shell= for the container itself, plus a
wrapper named after every tool above except /nuclei/, /dig/ and /host/ — reach
those with =web-run nuclei ...= or from =web-shell=. Each mounts the current
directory at //work/. Host networking is opt-in: set =WEB_NETWORK_HOST= to 1 to
add ~--network=host~ (needed only to reach a /localhost/ or /127.0.0.1/ target
on the host); remote targets use the default bridge. The wrappers only allocate a
TTY when both stdin and stdout are terminals, so they can be chained with pipes
and redirections like the native binaries:

#+begin_src shell
echo acme.com | gau | uro | anew urls.txt                # known URLs, deduped
katana -u https://acme.com -jc -jsl -o katana.txt        # crawl, parse JS for endpoints
cat urls.txt | subjs | anew js.txt                       # JS files out of a URL list
curl -s https://acme.com/app.js | js-beautify - > app.js # readable source
jsluice urls app.js ; jsluice secrets app.js             # endpoints / secrets from JS
cat js.txt | xnLinkFinder -sf acme.com                   # endpoints + params from JS -> output.txt
sourcemapper -url https://acme.com/app.js.map -output src/
waymore -i acme.com -mode U                              # archives, URLs only
cat urls.txt | unfurl paths | anew paths.txt             # path wordlist from URLs
cat urls.txt | gf xss | qsreplace FUZZ | anew xss.txt    # gf pattern -> one payload per param
cat urls.txt | dalfox pipe                               # scan a URL list for XSS
#+end_src

/gf/ ships tomnomnom's example patterns plus /Gf-Patterns/ (=gf -list= shows
them), so =gf xss=, =gf ssrf=, =gf redirect= and the rest work out of the box.

/SSTImap/ detects and exploits server-side template injection (Jinja2, Twig,
Freemarker, Velocity, Mako, Smarty and more). Point it at a reflecting
parameter; once it confirms an engine it can run commands or drop a shell:

#+begin_src shell
sstimap -u 'https://acme.com/page?name=John'      # detect the engine
sstimap -u 'https://acme.com/page?name=John' --os-cmd id   # if exploitable
#+end_src

Reflection, takeover and exposure checks:

#+begin_src shell
paramspider -d acme.com                          # hidden params mined from web archives
cat urls.txt | Gxss -c 50 | anew reflected.txt   # params whose value is reflected back
cat urls.txt | kxss                              # reflected + which special chars survive
corsy -i urls.txt                                # CORS misconfig: reflected origin + credentials
subzy run --targets subs.txt                     # subdomain-takeover fingerprinting
git-dumper http://acme.com/.git/ dump/           # rebuild an exposed .git over plain GETs
trufflehog filesystem dump/ --no-verification    # secrets in the dumped source, detect-only
jwt_tool <token>                                 # decode/inspect a JWT (alg:none, weak signing)
#+end_src

Run /trufflehog/ with =--no-verification= so it flags candidate secrets without
validating them against the live service, and treat the subdomain lists you feed
/subzy/ as scope input, not an invitation to scan out of scope.

/nuclei/ carries its full template set, baked in at build time, so scans run
offline with =-disable-update-check=; rebuild the image when you want fresher
templates.

/nomore403/ reads its payload lists from a folder; the image ships them and the
wrapper points at them automatically unless you pass your own =-f/--folder=.

/xnLinkFinder/ needs a scope with =-sf= and, upstream, reads stdin whenever stdin
is not a terminal, even with =-i=. Its wrapper therefore keeps a TTY as long as
stdin is one; take the results from =-o=/=-op= (or =output.txt=) rather than a
redirected stdout, and pipe a URL list into it instead of =-i= for batches.

/waymore/ writes to =results/<domain>/= under the current directory (the image's
config sets =DEFAULT_OUTPUT_DIR= to //work/). Default mode /B/ also downloads
every archived response, which is slow and large; =-mode U= for URLs only.

/katana/ =-headless= (and =-hybrid=) run on a chromium baked into the image
(about 760MB of it), so DOM-rendered SPAs crawl on any host, servers without a
browser included. The wrapper adds
=-system-chrome-path /usr/bin/chromium -no-sandbox= whenever a browser mode is
requested, which keeps katana from downloading its own glibc chrome (it cannot
run on Alpine); pass your own
=-system-chrome-path= or =-chrome-ws-url= and the wrapper stays out of the way.

#+begin_src shell
katana -u https://acme.com -headless -jc -o katana.txt   # render JS, crawl the DOM
#+end_src
